# PDFer

Lightweight powerful PDF editor on Rust.

Редактор PDF на Rust: GPUI для интерфейса, pdfium для разбора и растеризации.
Задача — быстрая и точная ручная правка текста в документах, где автоматический
перевод или конвертация дали кривой результат.

## Готовая сборка

Портативная сборка для Windows x64 лежит в
[релизах](https://github.com/iaa2005/pdfer/releases): распаковать архив и
запустить `PDFer.exe`. Установка не нужна, всё лежит в одной папке — `PDFer.exe`
рядом с `pdfium.dll`. Настройки и список недавних пишутся в `%APPDATA%\PDFer\`.

## Сборка и запуск

```bash
cargo run -p app -- book.pdf
```

Требуется MSVC-тулчейн (Visual Studio Build Tools) и `vendor/pdfium/bin/pdfium.dll`.
DLL не хранится в репозитории — поставить её можно так:

```bash
curl -L -o pdfium.tgz https://github.com/bblanchon/pdfium-binaries/releases/download/chromium%2F7881/pdfium-win-x64.tgz && mkdir -p vendor/pdfium && tar -xzf pdfium.tgz -C vendor/pdfium
```

Версия сборки pdfium (**7881**) выбрана не случайно: `pdfium-render 0.9.3`
генерирует биндинги под ревизию `pdfium_7881`. Другая ревизия DLL — это
рассинхрон ABI, который проявится не при сборке, а в рантайме.

Диагностика ядра без интерфейса — самый быстрый способ проверить разбор
абзацев на своей вёрстке:

```bash
cargo run -p pdfcore --example inspect -- book.pdf 12
```

## Устройство

```
crates/pdfcore   headless-ядро: pdfium, рендер, кэш, модель документа
crates/app       интерфейс на GPUI
vendor/pdfium    бинарь pdfium (не в репозитории)
```

`pdfcore` ничего не знает про UI. Всё, что не требует pdfium — геометрия,
модель, склейка блоков, кэш — чистый Rust под обычными юнит-тестами; работа с
pdfium проверяется сквозными тестами на PDF, который генерируется прямо в
тестах через lopdf.

### Три решения, на которых всё держится

**Один поток рендера, а не пул.** `Pdfium::new` содержит
`assert!(BINDINGS.get().is_none())` — библиотека допускает единственный
экземпляр на процесс и не даёт гарантий при параллельном доступе к документу.
Потери нет: замер на A4 с текстом даёт **2.3 мс на страницу**, то есть около
430 страниц в секунду с одного потока. Узкое место при прокрутке — не рендер.

**Масштаб квантуется.** При плавном зуме каждый кадр даёт новое значение
scale, и кэш промахивался бы всегда. Бакеты растут геометрически, по четыре на
удвоение; промежуточные значения показываются растяжением ближайшего.
Вытеснение считается в байтах, а не в записях: разворот A3 при 400% весит как
три сотни миниатюр.

**Модель документа не повторяет структуру PDF.** В файле нет ни абзацев, ни
стилей — только позиционированные глифы. Абзацы восстанавливаются при открытии
по геометрии и переписываются обратно при сохранении. Это единственный способ
дать предсказуемую правку с перевёрсткой: раскладку считаем мы, поэтому то, что
на экране, и то, что в файле, совпадает по построению.

### Порядок каналов

pdfium и gpui сходятся на BGRA, поэтому растр уходит на GPU без единого прохода
по пикселям. Но задаром это не достаётся: `pdfium-render` **по умолчанию
включает** `FPDF_REVERSE_BYTE_ORDER`, и буфер приходит в RGBA. Для gpui,
который трактует его как BGRA, это выглядит перестановкой красного и синего —
дерево на фотографии становится синим, а текст на белом остаётся неотличимым,
из-за чего ошибка легко живёт незамеченной. Флаг снят явным
`set_reverse_byte_order(false)`, а порядок закреплён тестом
`rendered_pixels_are_in_bgra_order`: он рисует чистый красный и проверяет, что
байты легли как `[0, 0, 255, 255]`.

Внутри приложения байты везде ходят в BGRA. Перестановка нужна ровно в одном
месте — при сохранении превью в PNG, который хранит RGBA.

Если снова возникнут сомнения в цветах, есть проба:

```bash
cargo run -p pdfcore --example probe_color -- book.pdf 11
```

Она сохраняет два PNG из одних и тех же байтов — с перестановкой и без; какой
выглядит правильно, тот порядок pdfium и отдаёт.

### Восстановление абзацев

Два шага, `crates/pdfcore/src/blocks.rs`:

1. **Символы → строки.** Объединение по совпадению базовой линии, разрыв на
   широких горизонтальных зазорах — иначе левая и правая колонки разворота
   склеятся в одну строку. Пробелы восстанавливаются по расстоянию: в PDF слова
   сплошь и рядом разделены только позиционированием, без глифа пробела.
2. **Строки → абзацы.** Строка ищет среди *открытых* блоков ближайший
   совместимый сверху, а не приписывается к последнему подряд. В
   многоколоночной вёрстке строки соседних колонок чередуются при обходе сверху
   вниз, и последовательная склейка на них разваливается.

Совместимость проверяется по горизонтальному перекрытию (различает колонки),
отношению кеглей (отрывает заголовок от текста), шагу базовых линий
относительно медианного интерлиньяжа блока (ловит отбивку между абзацами) и
выравниванию краёв — с отдельным исключением для абзацного отступа первой
строки. Выключка (левая, по центру, правая, по формату) восстанавливается по
разбросу краёв.

Все пороги заданы в долях кегля, а не в пунктах: настройки, подобранные на
книге 10 pt, иначе разваливаются на плакате 40 pt. Крутить их — в
`BlockOptions`.

## Правка текста

Клик по абзацу ставит поле ввода **прямо на его место** на странице, а над
блоком всплывает панель формата: `B`, `I`, `U`, гарнитура с поиском, кегль,
шаблоны. «Применить» переписывает абзац в документ, `Ctrl+S` кладёт результат в
`<имя>_edited.pdf` **рядом с исходником**. Оригинал не перезаписывается
никогда: правка PDF необратима, а открытый файл вполне может быть единственной
копией книги.

Панель и поле лежат внутри элемента страницы, поэтому пользуются той же
системой координат, что и документ: при прокрутке и зуме они едут вместе с
абзацем, и пересчитывать их положение не нужно.

Шаблоны — именованные наборы «гарнитура + кегль + начертание». `＋` сохраняет
текущее оформление, клик применяет, `Alt`+клик удаляет. Хранятся между
запусками в `%APPDATA%\pdf-editor\templates.json`.

Механика замены (`crates/pdfcore/src/edit.rs`): старые текстовые объекты блока
удаляются целиком, текст заново разбивается на строки по ширине блока и
кладётся обратно — по одному объекту на строку, от верхней границы вниз с
исходным интерлиньяжем. Ширина строк меряется самим pdfium, тем же кодом,
который потом будет их рисовать: метрики из стороннего движка разошлись бы на
доли пункта, а на длинной строке это накапливается и текст вылезает за поле.

### Чего правка пока не умеет

Блок правится **целиком и одним оформлением**. Поле ввода встаёт на место
абзаца и набирается гарнитурой самого документа — встроенная программа шрифта
отдаётся движку интерфейса, — но это всё ещё поле ввода, а не текст на
странице: цвет символов задаёт тема приложения, а не документ, и разного
оформления внутри одного абзаца нет.

Упирается это в `Input` из gpui-component: цвет текста он берёт прямо из
`theme().foreground` (`input/element.rs:964`), переопределить его нечем, а
`Theme` в gpui-component — глобальный объект без области видимости. Разного
оформления по кускам текста у него тоже нет.

Настоящая правка «как в Acrobat» требует собственного текстового элемента:
своей раскладки по ранам, каретки, выделения, обработки клавиатуры и ввода. Это
отдельная работа, а не настройка существующего поля.

### Оформление по кускам

Абзац задаётся последовательностью `StyledSpan` — у каждого куска своя
гарнитура, кегль, цвет, положение относительно базовой линии и подчёркивание.
Внутри одного `BT` текстовая матрица сдвигается сама после каждого показа,
поэтому куски одной строки идут подряд без нового `Tm`, а `Tf`, оператор цвета
и `Ts` выставляются только при смене.

Три вещи, которые в PDF устроены не так, как ожидается:

- **Индексы** — не свойство символа, а уменьшенный кегль плюс подъём `Ts`.
  Подъём обязательно возвращается к нулю в конце строки, иначе утекает на
  следующую.
- **Подчёркивание** — не свойство текста, а отдельная фигура. Рисуется после
  `ET` в системе координат строки, поэтому следует за поворотом абзаца.
- **Поворот** — накладывается на линейную часть исходной матрицы, а не
  заменяет её: там уже может сидеть наклон или нестандартный масштаб.

Проверено тестом `one_block_carries_several_styles_at_once`: абзац из пяти
кусков с нижним индексом, надстрочной сноской и красным подчёркнутым хвостом
переживает сохранение, вычитывается обратно целиком, индексы остаются мельче
основного текста — и вне блока по-прежнему ноль изменённых пикселей.

### Встраивание шрифтов

Пока оформление не трогали, правка идёт прежним шрифтом абзаца и в файл ничего
не добавляется. Как только сменили гарнитуру или начертание, системный шрифт
встраивается: собирается `Type0` с кодировкой `Identity-H` и потомком
`CIDFontType2`.

Кодировка выбрана не случайно: однобайтные ограничены 256 знаками, и кириллица
в них не помещается. При `Identity-H` в строке лежат прямо номера глифов, а
`CIDToGIDMap /Identity` говорит читателю, что номер CID и есть номер глифа.

Обязательная часть — таблица `ToUnicode`, обратное соответствие «номер глифа →
символ». Без неё текст нельзя ни скопировать, ни найти поиском, ни прочитать
обратно — а обратно его читает и сам редактор, когда заново разбирает страницу
на блоки. Это проверено тестом
`embedded_font_brings_cyrillic_into_a_latin_document`: он пишет кириллицу в
документ, где её нет, сохраняет, переоткрывает, убеждается, что текст
вычитывается, и заодно требует **ноль** изменений пикселей вне блока.

Шрифт кладётся целиком, без выделения подмножества: любой символ, который
понадобится потом, гарантированно найдётся. Файл тяжелеет на размер гарнитуры —
за предсказуемость это приемлемая плата.

### Шрифты

Пока оформление не трогали, правка идёт **прежним шрифтом блока** — встраивать
нечего, файл не растёт от исправления одной опечатки. Как только нажали `B`,
`I`, `U`, сменили гарнитуру или кегль, в документ встраивается системный шрифт:
иначе полужирного начертания взять неоткуда, а во встроенном подмножестве часто
нет и половины нужных глифов.

Встраивание идёт с `is_cid = true` — без этого шрифт кодируется однобайтно и
кириллица превращается в мусор. Это же снимает ограничение подмножеств: набрать
русский текст поверх латинского абзаца можно, выбрав в панели любую системную
гарнитуру. Проверено тестом `embedded_font_carries_cyrillic_through_save`.

Индекс системных шрифтов (около 550 файлов, почти полгигабайта на типичной
Windows) строится один раз за сеанс и прогревается в фоне при открытии
документа, чтобы клик по `B` не ждал сканирования.

Подчёркивание в PDF не свойство текста, а линия под ним: она рисуется отдельным
объектом по измеренной ширине строки.

Правка **отклоняется**, а не выполняется частично, если текстовый объект
пересекает границу блока — так бывает в файлах, где весь текст страницы выведен
одним оператором. Молча удалить такой объект значило бы стереть соседний текст.

### Почему правка идёт мимо pdfium

Первая версия правки работала через объектную модель pdfium и
`FPDFPage_GenerateContent`. На настоящей книге она разрушала страницу: замена
одного абзаца стирала разрядку и цвета у соседних заголовков, превращала
подписи осей в чёрные квадраты, а новый текст не отрисовывался после
сохранения. Разошлось 4.1% пикселей страницы.

Пошаговая проба показала, что по отдельности безвредны и пересборка потока, и
встраивание шрифта, и временные объекты для замера. Ломает сочетание:
`GenerateContent` собирает поток заново из объектной модели, и всё, что эта
модель не воспроизводит точно — межбуквенный интервал, цвета заливки,
нестандартные кодировки, — теряется у объектов, которых правка вообще не
касалась.

Вывод: объектная модель pdfium годится для чтения и растеризации, но не для
записи. Теперь правка идёт через `lopdf` и поток содержимого напрямую, а pdfium
после каждой правки просто перечитывает изменённые байты. Записывать он не
может ничего в принципе — значит и испортить не может.

Регрессия закрыта тестом `editing_a_block_leaves_the_rest_of_the_page_untouched`:
он сравнивает страницу попиксельно и требует **ноль** изменений за пределами
правленого блока. Прежний тест проверял, что текст извлекается после
переоткрытия, и потому дефект пропустил.

## Что уже работает

- Стартовая страница с недавними документами: сетка превью, открытие по клику
- Открытие любого PDF — системным диалогом или перетаскиванием файла в окно
- Открытие документа, геометрия 700 страниц за **20 мс** (без загрузки страниц)
- Виртуализированная лента страниц и панель миниатюр, следующая за лентой
- Фоновая растеризация с упреждением по ходу прокрутки, LRU-кэш растров
- Разбор текстовых блоков со стилями; клавиша `B` показывает их рамками поверх
  страницы — так удобно проверять пороги на своей вёрстке
- Правка текста абзаца с перевёрсткой и сохранением в отдельный файл
- Зум `Ctrl +` / `Ctrl −` / `Ctrl 0`, сохранение `Ctrl+S`, снять выделение `Esc`

### Где лежат данные

`%APPDATA%\PDFer\` — `recents.json` со списком недавних и `thumbnails\` с
превью первых страниц. Имя файла превью выводится из пути документа
детерминированно (FNV-1a, а не `DefaultHasher`, — тот не гарантирует
стабильность между запусками), поэтому стартовая страница не открывает ни
одного PDF, чтобы показать сетку, и остаётся мгновенной при любом размере
списка. Запись, чей файл исчез, показывается тусклой и убирается кликом.

## Чего ещё нет

1. **Отмена правки.** Undo/redo не сделаны, а правка меняет документ в памяти
   сразу. Пока единственный откат — закрыть документ, не сохраняя: исходный
   файл не трогается в любом случае.
2. **Операции со страницами.** Повернуть, удалить, вставить пустую,
   переставить. `FPDFPage_New`, `FPDFPage_Delete`, `FPDFPage_SetRotation`,
   `FPDF_MovePages` — всё есть в этой сборке.
3. **Правка отдельных слов внутри абзаца.** Сейчас блок переписывается целиком,
   поэтому выделить и выделить полужирным одно слово нельзя — оформление
   применяется ко всему абзацу.
4. **Цвет текста в панели.** Цвет исходного абзаца при правке сохраняется, но
   поменять его пока нельзя.
5. **Повёрнутый текст.** Символы с углом больше 1° исключаются из разбора
   абзацев (их число видно в `PageText::rotated_chars`). Модель абзацев
   рассчитана на горизонтальный текст.
